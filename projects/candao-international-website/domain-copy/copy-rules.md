# 餐道行业文案生成规则

版本：v1.1  
日期：2026-08-25

## 1. 通用生成流程

凡涉及 UI 文案、原型内容、后台页面、数据大屏、页面示例数据、状态提示或产品页面说明，必须按以下流程执行：

1. 识别目标角色：决策者、总部运营、门店、IT、配送、财务、市场、顾客、销售或支持。
2. 识别页面任务：建立认知、确认场景、展示能力、验证接入、证明案例、建立公司可信、降低疑问、完成转化。
3. 读取 `business-context.md`、`glossary.yaml`、`copy-rules.md`，必要时读取 `examples.md` 和 `copy-qa-cases.md`。
4. 使用 `glossary.yaml` 中的标准术语，不擅自替换受保护术语。
5. 按组件类型生成文案，不用同一种长段落覆盖所有 UI。
6. 不创造未确认指标、状态、流程、客户、认证、SLA 或合作状态。
7. 不用空泛价值描述代替业务对象、状态、条件和下一步操作。
8. 精简时必须保留业务对象、状态、条件、数据口径和下一步操作。
9. 输出前运行自动 QA；未通过时先修改一次，再输出检查后的最终版本。
10. 若文本已 `approved_and_locked`，原型构建阶段只允许调整布局，不允许删除、缩写或改写。

## 1.1 品牌显示规则

- 中文、繁體中文、项目叙述和官网默认显示品牌名统一使用「餐道」。
- `Candao` 仅在英文 Locale、英文法定名、文件名、URL、代码、路径或精确引用来源时保留。
- Home、Customers、About、Demo 等繁體中文页面不得把 `Candao` 当作默认品牌显示。
- 页面名、Frame 名、代码目录、文件名和英文内容库可按技术或英文语境保留 `Candao`。

## 1.2 已确认展示边界

- Home：Hero 下方可使用 Logo 带，引用 `assets/logo/candao-blue-logo.svg`，与 Hero 风格融合，不把 Home 做成客户案例页。
- Customers：可使用 PPT Slide 11 的 Performance 数据；客户案例使用实名客户，叙事深度参考 PPT，并突出前后对比数据。
- 产品状态：订单、门店、配送、财务相关状态是真实产品流转状态，应通过产品截图或截图式界面表达一个页面内的多状态流转，不为每个状态单独设计模块。
- 低保真完全确认后，才将内容按前端模式结合 Remotion 制作动效素材，再进入 Stitch 或 React 前端。
- English 内容库在繁體中文内容验收后生成。

## 1.3 产品名大小写敏感规则

- 产品名、服务名、技术名和客户名必须按 `glossary.yaml` 的标准形态显示。
- `iDMS` 是大小写敏感产品名：首字母 `i` 必须小写，`DMS` 必须大写；不得写成 `IDMS`、`Idms`、`idms`、`iDms` 或 `IdMS`。
- `SaaS` 是大小写敏感术语：两个 `a` 必须小写；不得写成 `SAAS`、`Saas` 或 `saas`。
- 原型、Figma、Stitch、React 和 CSS 不能使用会改变文字显示的统一大小写规则处理受保护术语，例如 `text-transform: uppercase`、`lowercase` 或 `capitalize`。
- 若设计需要使用大写视觉风格，只能换布局、字号、字重、间距或容器样式，不得牺牲产品名的识别性。

## 1.4 英文来源词的中文生产表达

- `Finance Center` 的直接来源是 PPT `Data Asset` 部分，可在证据矩阵、精确来源引用、英文 Locale、文件名、URL 或代码标识中保留。
- 中文 / 繁體中文官网、Figma、Stitch、React、Web Prototype 和截图式界面不得把 `Finance Center` 作为可见展示词。
- 简体内部说明默认写「财务对账」；繁體中文生产稿默认写「財務對賬」。
- 当需要说明能力对象时，优先写成「平台订单与 OMS 订单对账」「金额差异、状态差异和漏单识别」，不要只写「財務中心」。
- `CDBI / Finance Center`、`CDBI / Finance` 和 `OMS / Finance / CDBI` 在繁體中文生产稿中分别改为 `CDBI / 財務對賬`、`CDBI / 財務對賬` 和 `OMS / 財務對賬 / CDBI`。

## 2. 页面标题

必须包含：

- 行业对象或业务对象，例如订单、餐单、门店、配送、会员、财务、数据、接入；
- 页面任务，例如建立认知、确认场景、展示能力、验证接入、证明落地；
- 餐道特定产品或业务事实，避免可替换成任意 SaaS。

禁止：

- “让业务更高效”“智慧餐饮新体验”“数字化增长平台”这类泛化标题；
- 为了简短删除对象，例如把“多平台外卖订单”缩成“订单”；
- 把 `OMS / DMS / iDMS / CDBI / 財務對賬` 改成泛称。

## 3. 页面说明

必须回答：

- 谁在什么场景遇到什么问题；
- 哪个业务对象或状态需要被管理；
- 餐道通过哪些产品能力承接；
- 下一步用户应该看能力、看案例、看接入还是预约演示。

建议长度：

- 官网首屏说明：60-120 个繁中文字；
- 原型说明：可略长，但不得塞入无证据价值词；
- 后台页面说明：30-70 个繁中文字，优先讲状态和操作。

## 4. 指标卡

必须包含：

- 指标名称；
- 数值；
- 时间 / 口径 / 来源；
- 适用对象。

规则：

- 只能使用 `glossary.yaml` 的 `allowed_metrics` 或当前任务明确给出的授权指标。
- 不得创造百分比、增长率、门店数、订单量或 SLA。
- 指标卡标题必须是业务对象，不用“成绩”“能力”“价值”这类空词。

## 5. 表格字段

字段必须可被真实后台理解。优先使用：

- 订单编号、渠道、门店、餐单、订单状态、支付状态、配送状态、异常类型、处理人、更新时间、下一步操作；
- 骑手、配送距离、派单方式、预计送达、超时状态、第三方转派状态；
- 对账单号、平台订单号、OMS 订单号、金额差异、状态差异、漏单标记。

禁止：

- “效率分”“体验值”“智能指数”等无定义字段；
- 为了排版把状态列、异常列、下一步操作列删掉。

## 6. 图表标题

必须说明：

- 统计对象；
- 时间范围；
- 维度；
- 决策用途。

示例：

- `各平台訂單量與門店接單狀態`
- `配送超時與第三方轉派趨勢`
- `平台訂單與 OMS 訂單對賬差異`

## 7. 按钮

按钮只表达明确动作。

推荐：

- `查看平台能力`
- `預約相似場景演示`
- `同步餐單`
- `查看異常訂單`
- `轉派第三方配送`
- `重新對賬`

禁止：

- `了解更多` 单独出现；
- `立即赋能`、`开启增长`、`探索未来`；
- 按钮改写已锁定 CTA。

## 8. 表单

表单说明必须说明：

- 谁填写；
- 填写目的；
- 哪些字段影响后续演示或接入判断；
- 提交后的下一步。

字段建议：

- 公司 / 品牌名称；
- 联系人；
- 角色；
- 市场 / 地区；
- 门店规模；
- 当前渠道；
- 需要处理的问题；
- 已使用系统；
- 期望演示场景。

## 9. 成功提示

必须包含：

- 操作对象；
- 当前状态；
- 下一步。

示例：

- `餐單同步任務已建立，系統會更新各平台餐單與售罄狀態。你可以在同步記錄查看結果。`

## 10. 错误提示

必须包含：

- 出错对象；
- 原因或可见状态；
- 下一步操作；
- 不可用模糊恐吓或技术堆砌。

示例：

- `此訂單缺少配送坐標，暫時無法派單。請補充地址或轉交門店人工處理。`

## 11. 空状态

必须包含：

- 当前没有什么对象；
- 为什么没有；
- 用户可以做什么；
- 不得写“暂无数据”后结束。

示例：

- `目前沒有待處理異常訂單。若門店接單超時、退款未處理或配送狀態中斷，系統會在此顯示。`

## 12. 异常预警

必须包含：

- 异常对象；
- 异常状态；
- 触发条件；
- 影响；
- 下一步操作。

示例：

- `門店 A 有 3 張外賣訂單接單超時超過 5 分鐘，可能影響出餐與配送。請通知門店接單或改由營運人員處理。`

## 13. 原型阶段禁止擅自删减

低保真、Figma、Stitch、React 原型阶段只允许：

- 调整布局；
- 调整换行；
- 调整容器宽度；
- 标注溢出风险；
- 请求业务方确认删减方案。

不允许：

- 删除已锁定文本；
- 把真实业务文案换成占位符；
- 为了排版将“多平台订单 + 门店 + 配送 + 异常”缩成“业务流程”；
- 将已确认指标删成“数据表现”；
- 改写受保护术语。
- 使用 `text-transform`、自动大小写转换或样式规则把 `iDMS`、`SaaS`、`AMS / Connector`、客户名、产品名等受保护术语改成错误大小写。

如果发生文字溢出，必须报告：

```text
页面位置：
当前文字：
当前长度：
可用空间：
溢出原因：
建议调整方式：
是否需要业务确认：
```
