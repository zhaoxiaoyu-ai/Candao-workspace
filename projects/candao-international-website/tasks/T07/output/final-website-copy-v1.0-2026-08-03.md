| Practical | 从订单、门店、配送、数据和系统连接等真实问题开始 | Built around daily restaurant workflows |
| Connected | 表达跨渠道、跨门店、跨系统的流程连接 | Across channels, stores and systems |
| Trustworthy | 用能力、流程、授权案例和确认状态建立信任 | Clearer visibility, practical implementation support |

### 18.1 推荐英文句式

- Built for complex restaurant operations across channels, stores and markets.
- Simplify multi-channel restaurant operations without adding complexity for teams.
- Give headquarters better visibility while helping stores stay focused on service.
- Connect ordering, delivery, store workflows and operational data in one platform.
- Plan system integrations around the operating workflows your teams already use.

### 18.2 避免英文句式

- Overly generic SaaS claims that could apply to any industry.
- Claims based only on `all-in-one`, `best-in-class`, `leading`, or `AI-powered` without proof.
- Product-only wording such as `OMS features`, `DMS module`, or `QR ordering tool` as first-layer website messaging.
- Unverified proof points, customer names, certification claims, SLA promises or integration statuses.

## 19. Solutions vs Platform Content Boundary

T08 UX 必须保持 `Solutions` 与 `Products / Platform` 的内容边界，避免两个页面都在重复讲订单、配送和数据。

| 页面层级 | 核心问题 | 内容角色 | 用户心理 | CTA |
| --- | --- | --- | --- | --- |
| Solutions | 我的业务问题是什么？ | Business outcome layer | “我遇到的场景是否被理解？” | Find Your Solution / Contact Sales |
| Products / Platform | Candao 如何实现？ | Capability layer | “这个平台如何支持流程？” | Explore Platform / Book a Demo |
| Product Capability Pages | 某个能力如何工作？ | Workflow + UI demo layer | “这个能力在实际操作中如何发生？” | Book a Demo / View Integrations |
| Cases / Customers | 有没有可信证明？ | Proof layer | “类似客户如何验证价值？” | Contact Sales / Discuss a Relevant Story |

执行规则：

- `Solutions` 页面先讲用户问题、业务场景和结果，不先展示功能清单。
- `Platform` 页面先讲能力架构、系统关系和 UI 演示，不重复写成行业场景页。
- `Order Management`、`Delivery Management` 等产品能力页必须遵循：场景问题 → 操作流程 → 产品界面 → 业务结果 → CTA。
- `Cases` 页面在客户授权前只承接证明结构，不补充具体事实。

## 21. Asset Direction

本节用于约束 T08 UX、T10 视觉和后续素材准备，确保官网视觉服务于餐饮营运理解，而不是变成泛科技或泛商务页面。

### 21.1 推荐素材类型

| 场景 | 推荐素材 | 用途 |
| --- | --- | --- |
| Home Hero | 餐厅高峰营运视频、前台接单、后厨出餐、门店协作 | 建立真实餐饮营运感 |
| Platform Overview | 产品 UI 动效、能力地图、订单 / 菜单 / 配送 / 数据流 | 解释 Candao 是统一平台 |
| Order Management | 多渠道订单进入统一队列、状态变化、总部异常视图 | 展示订单从分散到集中 |
| Delivery Management | 地图、骑手状态、配送队列、履约时间线 | 展示高峰配送调度 |
| Solutions | 连锁门店、总部运营、区域管理、门店执行 | 展示业务场景 |
| Integrations | 系统类别图、连接线、数据流、表单入口 | 建立系统连接可信度 |
| Cases | 案例模板、场景标签、Challenge / Solution / Result 框架 | 在无授权时保留证明结构 |
| Company | 团队、服务支持、餐饮营运协作场景 | 建立公司可信度 |

### 21.2 避免素材类型

- 普通办公室、会议室、商务握手和过度摆拍团队照。
- 与餐饮营运无关的抽象科技背景、数据隧道、3D 球体和 AI 概念图。
- 大量静态后台截图堆叠，导致页面像产品说明书。
- 未授权客户 Logo、客户门店照片、客户评价、具体业务数据。
- 无业务信息的库存图片，例如只展示咖啡、餐盘或餐桌氛围。

### 21.3 UI Motion 原则

- UI 动效必须服务业务流程理解：订单进入、状态变化、配送调度、数据回流。
- 动效节奏应克制、清晰、可读，不追求炫技。
- 产品 UI 可使用抽象化界面表达，不暴露未确认真实客户数据。
- 移动端优先保证阅读和 CTA 清晰，复杂动效可降级为静态步骤或轻量切换。
