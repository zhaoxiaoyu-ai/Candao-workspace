## 2. 最终品牌定位

### 2.1 中文定位

全球餐饮智能运营 SaaS 平台

### 2.2 English Positioning

Intelligent SaaS Platform for Global Restaurant Operations

### 2.3 业务化解释

Candao 帮助连锁餐饮品牌统一管理多渠道订单、菜单、配送、集成与营运数据，让总部看清业务，让门店减少重复操作，让配送更可控，让现有 POS、外卖平台、支付、CRM 和配送生态可以被连接起来。

### 2.4 定位解释

该定位保留了三个层级：

| 层级 | 作用 |
| --- | --- |
| 全球餐饮 | 对应国际官网，不局限于中国市场或单一区域 |
| 智能运营 | 承接订单、菜单、配送、数据、集成和异常监控，不只是点餐工具 |
| SaaS 平台 | 建立国际 B2B / SaaS 品牌感，区别于项目外包或单点系统 |

### 2.5 不采用的定位方向

| 不采用方向 | 原因 |
| --- | --- |
| 餐饮系统供应商 | 过于传统，容易让国际客户理解为软件外包或单系统供应 |
| OMS / DMS 解决方案 | 内部产品名不适合作为国际官网第一层表达 |
| 全渠道点餐平台 | 过窄，无法覆盖配送、数据、集成和门店运营 |
| 香港餐饮数字化服务商 | 本地可信度强，但限制国际官网品牌高度 |
| AI 餐饮平台 | 当前 AI 能力未形成主线，不应抢占定位 |

## 3. 用户画像

### 3.1 核心用户一：海外连锁餐饮集团

典型对象：

- 香港、新加坡、英国、澳洲、北美等市场的区域性或国际连锁餐饮集团；
- 多门店、多品牌、多渠道、多配送和多系统并行的餐饮企业；
- 需要总部统一管理、门店稳定执行和跨系统数据整合的组织。

核心问题：

- 多个平台订单难统一；
- 门店频繁切换系统和设备；
- 菜单、库存和门店信息重复维护；
- 高峰期订单与配送异常难以及时处理；
- 总部缺少跨门店、跨渠道和跨区域经营视图。

页面关注：

- Home；
- Solutions；
- Products / Platform；
- Integrations；
- Case Studies；
- Security / Trust。

主要 CTA：

- Book a Demo；
- Contact Sales。

### 3.2 核心用户二：餐饮经营者

典型对象：

- 餐饮品牌老板；
- 营运负责人；
- 区域经理；
- 门店管理者。

核心问题：

- 漏单、错单、超时单；
- 菜单和门店资料重复维护；
- 高峰配送不可控；
- 员工被多个后台、平台和设备拖住；
- 看不到系统对门店效率的直接帮助。

页面关注：

- Home；
- Solutions；
- Products；
- Case Studies；
- FAQ；
- Contact。

主要 CTA：

- Book a Demo。

### 3.3 核心用户三：技术合作伙伴

典型对象：

- POS 厂商；
- 支付服务商；
- 配送平台；
- CRM / 会员系统；
- 外卖平台；
- 区域实施或渠道伙伴。

核心问题：

- Candao 是否可集成；
- 如何合作；
- 是否有 API 或集成流程；
- 数据边界、安全和系统稳定性是否清晰；
- 合作是否能带来餐饮客户和生态价值。

页面关注：

- Integrations；
- Partner / Contact；
- About；
- Security；
- Resources。

主要 CTA：

- Partner With Us；
- Request Integration；
- Contact Sales。

## 4. 网站目标

### 4.1 P0：品牌展示与可信建立

国际官网第一阶段必须先解决“Candao 是谁、是否可信、是否懂餐饮运营”的问题。

必须建立的认知：

- Candao 是餐饮运营 SaaS 平台，不是单点工具；
- Candao 理解连锁餐饮多平台、多门店、多配送、多系统集成的复杂度；
- Candao 有香港及亚洲餐饮交付经验；
- Candao 有企业级安全、服务和技术能力，但具体数据与认证需要确认后公开。

### 4.2 P0：Demo 与销售线索转化

官网必须承接销售线索。

主 CTA：

- Book a Demo；
- Contact Sales。

建议转化路径：

```text
Home
→ Solutions / Products
→ Integrations / Case Studies
→ Book a Demo / Contact Sales
```

策略说明：

- 第一阶段不建议公开 Pricing 作为主导航重点；
- 企业级餐饮 SaaS 更适合通过 Contact Sales 和 Demo 了解场景后报价；
- Demo 表单字段和接收人仍需业务确认。

### 4.3 P1：合作伙伴获取

官网应支持技术合作伙伴和生态伙伴进入。

建议入口：

- Integrations；
- Partner / Contact；
- Request Integration；
- Contact Sales。

策略说明：

- Integrations 是国际官网的重要信任入口；
- 但未确认集成状态前，不得把平台 Logo 或合作状态写成确定事实；
- 可先在战略层规划分类：Delivery Platforms、POS、CRM、Third-party Logistics、Payment Gateway、API。

### 4.4 P1：产品理解

官网必须让用户快速理解 Candao 能力，但不能把首页做成产品说明书。

产品理解顺序：

```text
客户问题
→ 解决方案方向
→ 产品能力
→ 证明材料
→ CTA
```

## 5. 核心价值表达

### 5.1 核心价值主张

Candao 的核心价值不是“拥有多个系统”，而是：

- 将分散在多个平台、门店和系统中的订单、菜单、配送和数据统一管理；
- 减少门店重复操作和人工切换；
- 帮助总部掌握跨渠道、跨门店和跨区域运营情况；
- 在高峰期让配送和异常处理更可控；
- 通过集成能力连接客户已有 POS、支付、配送、会员和外卖生态。

### 5.2 表达公式

后续所有官网策略、页面结构和 Copy 应遵循：

```text
经营问题
→ Candao 解决方式
→ 业务结果
→ 可信证明
→ 下一步行动
```

### 5.3 推荐表达方向

| 业务问题 | 官网表达方向 | 承接能力 |
| --- | --- | --- |
| 多平台订单难管理 | 统一管理多渠道订单 | OMS / COMS、Order Management |
| 菜单重复维护 | 一次维护，多平台同步 | Menu and Store Management |
| 配送高峰不可控 | 自有与第三方配送统一调度 | Delivery Aggregator、DMS |
| 数据割裂 | 跨渠道经营数据看板 | Data Intelligence、Reporting Center |
| 系统孤岛 | 连接 POS、外卖、支付、CRM 和配送生态 | Integrations / API |
| 国际采购信任不足 | 用案例、认证、安全和服务能力建立可信度 | Case Studies、Security、About |

### 5.4 禁止表达方式

后续官网不应以以下方式作为第一层表达：

- OMS 系统；
- DMS 系统；
- COMS 系统；
- QR Code Ordering 系统；
- “我们提供一站式解决方案”这种泛化句；
- 未确认客户 Logo；
- 未确认规模数字；
- 未确认集成状态；
- 未确认 SLA 或认证承诺。

## 6. 官网核心叙事

### 6.1 首页讲什么

首页应讲：

> Candao 如何帮助餐饮品牌把分散的订单、菜单、配送和营运数据统一起来，让总部更清楚、门店更高效、配送更可控。

首页不应讲：

- Candao 有多少内部系统；
- 每个产品模块的完整功能；
- 大段公司历史；
- 未确认数据和客户背书。

### 6.2 用户第一眼应该理解什么

用户进入首页第一屏后，应立即理解：

- Candao 是服务餐饮运营的 SaaS 平台；
- 它解决的是多渠道订单、菜单、配送和数据割裂的问题；
- 它适合连锁餐饮、多门店运营和需要集成的平台生态；
- 下一步可以预约 Demo 或联系销售。

### 6.3 Candao 与竞品/传统系统供应商的差异

| 对比对象 | Candao 差异 |
| --- | --- |
| 传统餐饮系统供应商 | 不只提供单点系统，而是连接订单、菜单、配送、数据和集成 |
| 点餐体验平台 | 不只做顾客点餐体验，还覆盖门店和总部运营 |
| 第三方订单整合工具 | 不只接订单，还承接菜单、门店、配送、报表和财务对账 |
| 通用 SaaS 官网 | 更需要真实餐饮运营场景、香港/亚洲案例和交付可信度 |

## 7. 导航策略

### 7.1 推荐主导航

| 导航 | 角色 | 说明 |
| --- | --- | --- |
| Home | 品牌认知和转化入口 | 讲定位、问题、能力、信任和 CTA |
| Solutions | 业务场景入口 | 按客户问题和经营场景组织 |
| Products / Platform | 产品能力入口 | 讲 Candao 平台能力和模块边界 |
| Integrations | 生态可信入口 | 讲外卖、POS、支付、CRM、配送和 API |
| Customers / Case Studies | 信任验证入口 | 讲案例、结果和行业证明，需授权 |
| Resources | 内容与支持入口 | FAQ、Support、Press、Guides，第一阶段低承诺 |
| About | 公司可信入口 | 公司介绍、里程碑、服务能力、签约关系说明 |
| Contact / Demo | 转化入口 | Demo、Sales、Partner、Support 分流 |

### 7.2 Solutions 与 Products / Platform 的关系

冻结决策：

- `Solutions` 和 `Products / Platform` 建议分层保留。
- `Solutions` 是业务价值主入口。
- `Products / Platform` 是产品能力承接层。

分工：

| 维度 | Solutions | Products / Platform |
| --- | --- | --- |
| 第一问题 | 用户遇到什么经营问题 | Candao 有哪些平台能力 |
| 内容组织 | Restaurant Chains、Multi-store Operations、Delivery Operations、Digital Ordering | Order Management、Menu and Store Management、Delivery Management、Data Intelligence、Integrations |
| 表达重点 | 场景、结果、行业问题 | 能力、模块、UI、功能边界 |
| CTA | Book a Demo / Talk to Sales | Explore Product / Book a Demo |

### 7.3 Integrations 的定位

冻结决策：

- Integrations 应成为一级战略入口。
- 不建议放在 Products 下作为普通功能模块。

原因：

- 集成是国际餐饮 SaaS 的采购关键门槛；
- 技术合作伙伴也会从 Integrations 进入；
- 它同时支撑产品理解、可信证明和合作伙伴获取。

### 7.4 Resources 的定位

冻结决策：

- Resources 第一阶段不应做成高频内容中心。
- 先承接 Support、FAQ、Press、Guides 或 Show cases 的低承诺内容。

原因：

- 内容运营责任和更新频率未确认；
- 过早规划 Blog / Insights 会增加空置风险。

## 8. 首页内容逻辑

### 8.1 首页 Section 顺序

冻结的首页框架：

1. Hero  
   任务：建立定位和业务问题。  
   内容：一句话定位、业务化解释、主 CTA、餐饮运营场景 + UI 动效。

2. Trust Bar  
   任务：快速建立可信度。  
   内容：客户、认证、集成、服务能力或规模数据。  
   注意：未确认数字只做内部占位，不进入正式 Copy。

3. Problem Switcher  
   任务：让用户看到自己的问题。  
   内容：多平台订单、菜单重复维护、配送异常、数据割裂。

4. Capability Overview  
   任务：把复杂产品压缩成 4-5 个能力入口。  
   内容：订单、菜单、配送、数据、集成。

5. Solutions Preview  
   任务：按业务场景承接用户需求。  
   内容：连锁餐饮、多门店运营、自营点餐、配送管理。

6. Integrations Snapshot  
   任务：证明可接入现有生态。  
   内容：外卖平台、POS、支付、CRM、配送、API 分类。

7. Case Highlight  
   任务：用真实案例建立信任。  
   内容：香港客户或大型集团案例。  
   注意：客户名称、Logo、数据需授权。

8. Final CTA  
   任务：推动转化。  
   内容：Book a Demo / Contact Sales。

### 8.2 Hero 策略

Hero 表达重点：

- 统一订单；
- 统一菜单；
- 调度配送；
- 连接数据；
- 服务连锁餐饮运营。

Hero 视觉方向：

- 主视觉：真实餐饮运营场景；
- 辅助：浮层 SaaS UI；
- 表达：订单流转、菜单同步、配送状态、数据分析；
- 避免：纯 3D 科技视觉、抽象 AI 背景、软件截图堆叠、未确认数字大字报。

### 8.3 首页核心表达

首页核心表达应围绕：

- 分散订单集中管理；
- 多平台菜单统一维护；
- 自有和第三方配送协同；
- 总部营运数据可视；
- 现有技术生态可连接；
- 预约 Demo 进入下一步。

## 10. 内容原则

### 10.1 全站内容原则

后续所有页面内容必须遵循：

1. 从业务结果开始，而不是产品名称。
2. 从客户场景开始，而不是功能列表。
3. 从信任建立开始，而不是企业自述。
4. 从转化路径组织内容，而不是平均铺资料。

### 10.2 核心页面内容结构

每个核心页面必须包含：

| 内容层 | 说明 |
| --- | --- |
| 用户问题 | 用户进入该页面时最关心的问题 |
| 解决方案 | Candao 如何组织和解决这个问题 |
| 产品能力 | 支撑方案的具体能力 |
| 证明材料 | 客户、数据、认证、集成、服务能力 |
| CTA | Book a Demo、Contact Sales、Partner With Us 等 |

### 10.3 T06/T07 Copy Agent 规则

- T06/T07 必须输出繁体中文 + 英文官网内容。
- 不得输出简体中文正式网页文案。

## 12. 后续执行护栏

本节作为 T03 v1.1 补充，用于约束 T04 信息架构、T06/T07 Copy、T08 UX 和 T10/T11 视觉设计。后续任务可以细化执行方案，但不得推翻本节已冻结的战略边界。

### 12.1 品牌语气 Tone of Voice

Candao 国际官网的品牌语气应体现企业级 SaaS 的专业感，同时保持餐饮运营语境下的务实和可信。

推荐语气：

| 语气 | 执行说明 |
| --- | --- |
| 专业 | 表达平台能力、集成能力和企业级交付能力，但不堆砌技术术语 |
| 务实 | 关注订单、菜单、配送、门店和数据等真实运营问题 |
| 可信 | 基于经验、案例、服务和安全能力建立信任，不夸大未确认数据 |
| 国际化 | 避免中国软件官网常见套话，使用更接近国际 SaaS 的表达方式 |

避免表达：

- 一站式解决方案；
- 行业领先；
- 赋能企业；
- 全面提升效率；
- 数智化转型标杆；
- 用技术重塑餐饮未来。

推荐英文表达方向：

- Simplify restaurant operations；
- Connect every channel；
- Improve operational visibility；
- Manage orders, menus and delivery in one platform；
- Built for growing restaurant brands。

执行要求：

- T06/T07 可以基于以上方向生成繁体中文和英文官网 Copy；
- 英文 Copy 应优先清楚、克制、可信，避免过度营销化；
- 繁体中文 Copy 应适合香港及亚洲市场审核，不使用简体中文网页文案。

### 12.2 全站视觉原则

后续视觉设计必须围绕“真实餐饮运营场景 + SaaS UI 动效”展开。

视觉原则：

1. 优先使用真实商业餐饮场景，包括门店营运、厨房出单、前台接单、配送协调、总部运营等。
2. 产品能力通过 UI 动效、数据流、订单流和状态变化表达，而不是堆叠静态截图。
3. 视觉气质应接近国际 SaaS：简洁、高级、可信、信息清晰。
4. 摄影、视频和 UI 组合应服务业务理解，不做纯装饰。
5. 首页 Hero 可以使用餐厅运营场景视频或高质量摄影，并叠加轻量 SaaS UI 层。

避免方向：

- 纯 3D 科技视觉；
- 抽象 AI 背景；
- 大量插画替代真实业务；
- 与餐饮运营无关的概念图；
- 软件截图密集平铺；
- 过度未来感或加密科技感。

### 12.3 页面设计优先级

第一阶段设计投入应集中在品牌认知、产品理解、集成可信和转化闭环相关页面。

| 页面 | 英文名称 | 设计深度 | 设计投入说明 |
| --- | --- | --- | --- |
| 首页 | Home | ★★★★★ | 第一印象、核心叙事、视觉方向和 Demo 转化的主战场 |
| 平台/产品 | Products / Platform | ★★★★★ | 需要重点设计产品理解路径、UI 动效和能力结构 |
| 解决方案 | Solutions | ★★★★ | 需要清晰表达不同经营场景和用户问题 |
| 集成 | Integrations | ★★★★ | 需要建立生态连接、技术可信和合作入口 |
| 联系 / Demo | Contact / Book a Demo | ★★★★ | 直接影响销售线索转化，表单和信任提示必须清晰 |
| 客户案例 | Customers / Case Studies | ★★★ | 授权未确认前可先设计案例模板和占位结构 |
| 关于 | About | ★★ | 重点是可信信息和公司背景，不需要过度视觉化 |
| FAQ / Support | FAQ / Support | ★★ | 以清晰、可扫描的信息组织为主 |

### 12.4 产品展示体验原则

Products / Platform 页面和首页产品模块不得做成内部产品名或功能点列表。

产品展示应遵循：

```text
场景问题
→ 操作流程
→ 产品界面
→ 业务结果
→ 下一步行动
```

执行方式：

| 层级 | 说明 |
| --- | --- |
| 场景问题 | 先说明用户为什么需要该能力，例如订单分散、菜单重复维护、高峰配送不可控 |
| 操作流程 | 展示用户如何从接单、同步、调度、监控到分析完成关键任务 |
| 产品界面 | 用 UI 动效或重点界面说明 Candao 如何承接流程 |
| 业务结果 | 回到减少切换、降低错误、提升可视性、加强总部管控等结果 |
| CTA | 引导 Book a Demo、Contact Sales 或查看相关 Solution |

禁止方式：

- 以 OMS、DMS、COMS、QR Code Ordering 作为页面第一层信息；
- 大段罗列功能点；
- 将产品页写成操作说明书；
- 只展示后台截图，不解释客户问题和业务结果；
- 用过多内部系统名称替代用户可理解的业务语言。
