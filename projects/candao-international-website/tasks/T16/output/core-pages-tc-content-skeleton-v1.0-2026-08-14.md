## 2. Home / 首頁

頁面角色：

建立第一認知。首頁只回答「餐道是誰、為什麼複雜餐飲 O2O 營運需要它」，不展開完整產品手冊。

### 2.1 Hero: 餐飲 O2O 營運連接器

來源：

- OLD-SOLUTION-292
- PPT-OPMODEL
- PPT-SAAS

用戶問題：

我有多個訂單渠道、門店、POS、配送、會員和財務系統，餐道到底能幫我接住哪一段？

業務事實：

餐道以 Connector 思維，把訂單渠道、門店、菜單、配送、會員、支付、POS、財務與數據接入同一條營運鏈路。

標題方向：

```text
把複雜餐飲 O2O 營運，接成一個可管理的閉環
```

說明方向：

```text
餐道協助餐飲與零售品牌連接外賣平台、自有點餐入口、門店系統、配送資源、會員與營運數據，讓總部、門店與配送團隊能在同一條業務鏈路上協同處理訂單、菜單、履約與分析。
```

CTA 方向：

```text
了解餐道如何連接營運
預約產品演示
```

不可越界：

- 不放未確認客戶 Logo。
- 不放未確認規模數字。
- 不寫「全球領先」「唯一」「最完整」等未證實語句。

### 2.2 Complexity Map: 複雜營運不是單一系統問題

來源：

- PPT-OPMODEL
- PPT-OMS-PAIN

用戶問題：

我們的問題不是只有接單，而是渠道、門店、菜單、配送和數據都在分散。

業務事實：

PPT 中的 Operation Model 顯示餐飲營運牽涉 Order Flow、POS / KDS、CRM、ERP、外賣平台、Mini-programs、OMS、IDMS、Rider App、Monitoring 等節點。

標題方向：

```text
當訂單、門店、配送與數據分散，營運問題會一起放大
```

內容方向：

- 多個外賣平台需要切換後台；
- 菜單、庫存、售罄狀態需要跨渠道維護；
- 門店異常、訂單超時、配送狀態需要被即時看見；
- 財務與營運數據需要從不同來源回到同一個分析口徑。

展示方向：

```text
使用系統節點圖：Order Channel -> OMS -> Store / POS -> Delivery / DMS -> Data / Finance。
```

不可越界：

- 節點可以展示系統類型，不展示未確認品牌 Logo。

### 2.3 Operating Loop: 從下單到營運決策

來源：

- OLD-USERPAIN-290
- OLD-PAIN-284
- PPT-SAAS
- PPT-DATA

用戶問題：

餐道如何把前台交易變成後台可追蹤、可分析、可處理的營運閉環？

業務事實：

舊官網強調打通閉環、數據利用和價值提升；PPT 中則呈現訂單、菜單、配送、報表、財務對賬和 API 結構。

標題方向：

```text
從每一張訂單，到每一次營運判斷
```

流程方向：

```text
訂單進入 -> 菜單與庫存同步 -> 門店接單與異常提醒 -> 配送履約與狀態追蹤 -> 報表分析與財務對賬 -> 營運調整
```

不可越界：

- 不使用假 Dashboard 數字。
- 不把財務對賬寫成已覆蓋所有平台，除非後續確認。

### 2.4 Product System Preview: 產品體系入口

來源：

- OLD-PRODUCT-285
- PPT-COMPANY
- PPT-OMS-CORE

用戶問題：

餐道有哪些產品能力？它們分別解決什麼？

內容方向：

| 入口 | 標題方向 | 說明方向 | 導流 |
|---|---|---|---|
| OMS | 多渠道訂單與門店營運管理 | 承接外賣平台、自有入口、POS 與門店接單，統一處理訂單、餐品和門店狀態 | 前往平台 |
| CDBI / Data Asset | 營運數據與財務分析 | 匯總訂單、渠道、門店、財務與營運指標，支援報表、看板和對賬 | 查看數據能力 |
| iDMS | 聚合配送管理 | 協助門店呼叫配送、追蹤狀態、查看交易和處理配送異常 | 查看配送履約 |
| DMS | 自有騎手配送管理 | 支援自有騎手、智能派單、人工調度、第三方溢出、騎手 App 和監控報表 | 查看 DMS |
| AMS / Connector | 生態服務商接入 | 提供統一合作入口、標準接口與定制轉換中間件，連接營運生態 | 查看整合能力 |

不可越界：

- 產品命名需後續由業務確認。
- 不在首頁展開每個產品的完整功能。

## 3. Solutions / 解決方案

頁面角色：

讓用戶先從自己的業務場景進入，而不是從產品功能開始。Solutions 只講「問題、場景、角色壓力、業務結果方向」，不做產品手冊。

### 3.1 解決方案總覽：三個營運問題

來源：

- OLD-USERPAIN-290

標題方向：

```text
從閉環、數據到增長，重新梳理餐飲 O2O 營運
```

三個問題方向：

| 問題 | 內容方向 | 導向能力 |
|---|---|---|
| 打通閉環 | 訂單、門店、菜單、配送和會員不能停留在不同後台 | OMS、AMS、DMS |
| 數據利用 | 多渠道資料需要被整理成可分析、可對賬、可追蹤的營運資產 | CDBI、Finance Center |
| 價值提升 | 自有點餐、會員、營銷和配送能力需要回到品牌自己的營運節奏 | Mobile Ordering、Marketing、iDMS |

### 3.2 多渠道外賣營運

來源：

- OLD-TAKEOUT-379
- PPT-OMS-PAIN
- PPT-OMS-MODULES

用戶問題：

外賣平台多，門店和總部需要在多個後台切換，菜單、庫存、訂單和異常難以統一處理。

標題方向：

```text
讓多平台外賣訂單回到同一條處理鏈路
```

內容方向：

- 外賣平台訂單集中查看；
- 門店接單、打印、異常提醒進入統一流程；
- 菜單、庫存、售罄狀態可跨渠道維護；
- 訂單數據可回到報表和財務對賬。

推薦能力：

```text
OMS / COMS / SOMS / Menu Center / CDBI
```

不可越界：

- Foodpanda、Deliveroo 等平台名稱暫作內部參考，公開展示需確認。

### 3.3 多門店營運

來源：

- PPT-OMS-MODULES
- PPT-MOBILE

用戶問題：

總部、區域和門店需要維護不同渠道的店鋪資料、營業狀態、配送條件和菜單設定。

標題方向：

```text
讓總部設定、區域管理與門店執行保持同步
```

內容方向：

- 總部可統一維護門店基礎資料；
- 不同門店和區域可使用不同菜單與營業設定；
- 門店異常、訂單超時和接單問題可被監控；
- 報表可幫助管理團隊查看門店營運狀態。

推薦能力：

```text
Operation Management Center / Store Abnormity / Reporting Center
```

### 3.4 數字點餐與自助服務

來源：

- OLD-ONLINE-394
- OLD-WYW-461
- PPT-MOBILE

用戶問題：

顧客入口變多後，品牌需要把手機點餐、堂食掃碼、自有 H5、會員與門店接單接在一起。

標題方向：

```text
把顧客點餐入口，接回品牌自己的營運系統
```

內容方向：

- 支援外賣訂餐、堂食掃碼、預約下單和移動支付等入口；
- 顧客下單後，訂單可回到門店接單與後台管理；
- 會員權益、優惠通知和營銷活動可配合自有渠道運作；
- 數據可回流到品牌營運分析。

推薦能力：

```text
Mobile Ordering / Membership / Marketing / Store Order-taking
```

### 3.5 配送營運與履約

來源：

- OLD-DELIVERY-388
- PPT-IDMS
- PPT-DMS
- PPT-DMS-DISPATCH

用戶問題：

自有騎手、第三方物流和平台配送同時存在時，門店需要知道誰接單、誰取餐、是否超時、如何補充運力。

標題方向：

```text
把配送資源、騎手狀態與履約異常放回可控範圍
```

內容方向：

- 聚合配送可協助門店呼叫配送和追蹤狀態；
- DMS 支援自有騎手管理、智能派單、人工派單和第三方溢出；
- 訂單超時、配送異常和騎手位置可被監控；
- Consumer SMS 可讓顧客掌握配送進度。

推薦能力：

```text
iDMS / DMS / Dispatch / Rider App / Consumer SMS
```

不可越界：

- 不公開物流合作方名稱、價格表、服務承諾和性能數字。

### 3.6 數據化營運與財務對賬

來源：

- OLD-PAIN-284
- OLD-PRODUCT-285
- PPT-DATA

用戶問題：

多渠道資料分散，管理層和財務團隊難以快速看出訂單、營收、補貼、漏單和異常。

標題方向：

```text
讓營運數據不只被看見，也能被對賬和追蹤
```

內容方向：

- 支援多維報表和實時看板；
- 可按訂單、門店、渠道、商品、用戶和配送維度分析；
- Finance Center 可比對平台訂單和 OMS 訂單；
- 幫助發現金額、狀態、漏單等對賬異常。

推薦能力：

```text
CDBI / Reporting Center / Finance Center
```

### 3.7 系統託管與全渠道代運營

來源：

- OLD-PAIN-284

用戶問題：

部分商家不只需要系統，也需要持續維護全渠道資料、處理訂單、監督營運並根據數據調整方案。

標題方向：

```text
不只提供系統，也支援持續營運管理
```

內容方向：

- 支援全渠道信息更新和維護；
- 支援訂單處理和營運監督；
- 可根據數據分析結果制定營銷和自有渠道運營方案。

不可越界：

- 服務範圍、時段、交付方式和收費必須後續確認。

## 5. Integrations / 整合能力

頁面角色：

證明餐道連接的是餐飲 O2O 營運生態，不是裝飾性 Logo。

### 5.1 整合類型總覽

來源：

- OLD-BIZ-289
- PPT-SAAS

標題方向：

```text
連接餐飲 O2O 營運中的關鍵系統類型
```

分類方向：

| 類型 | 內容方向 |
|---|---|
| 外賣平台 | 接收外部訂單並回到 OMS |
| 自建系統 | H5、Web、小程序等自有點餐入口 |
| POS / KDS / 後廚 | 承接門店出單、收銀和後廚流程 |
| CRM / 會員 | 連接會員資料、權益和營銷活動 |
| 配送供應商 | 連接第三方物流、騎手公司和狀態回傳 |
| 線上支付 | 承接支付狀態和財務資料 |
| ERP / Finance / Supply Chain | 支援後續財務、供應鏈和企業管理資料流 |

不可越界：

- 不展示未確認 Logo。
- 不承諾已接所有系統。

### 5.2 Hong Kong Operation Eco-system

來源：

- PPT-OPMODEL

標題方向：

```text
面向香港餐飲營運生態的連接中樞
```

內容方向：

- 訂單來源可來自 Food Order Platform、Online Order Web / H5 等類型；
- 門店側需要連接 POS、支付、後廚和第三方系統；
- 配送側需要連接 Delivery、Rider Co. 和聚合配送能力；
- Can-Dao Connector 位於系統與業務流程之間，負責把資料和狀態接回營運鏈路。

不可越界：

- 地區、品牌和合作方名稱要經業務確認後再公開。

### 5.3 API and Data Flow

來源：

- PPT-SAAS
- OLD-PRODUCT-285

標題方向：

```text
訂單、菜單、用戶與基礎資料，都需要可追溯的數據流
```

內容方向：

- Menu API 支援菜單資料流；
- Order API 支援訂單資料流；
- User details API 支援用戶資料流；
- Basic info API 支援門店與基礎資料流；
- AMS / Connector 承接標準接口與定制轉換中間件。

不可越界：

- API 名稱可作內容方向，具體字段、權限和安全規格需確認。

### 5.4 POS / Store System Flow

外部訂單進入門店後，還要接住 POS、打印與後廚流程

### 5.5 Delivery Integration Flow

來源：

- OLD-DELIVERY-388

- PPT-DMS

配送整合不只呼叫運力，也要回傳狀態與異常

內容方向：

不可越界：
