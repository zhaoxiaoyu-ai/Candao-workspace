# T30 用户澄清与名词解释

## 用户最新澄清

### 1. 使用者

这个网页竞品分析 Agent 的最终使用者主要是设计师。

它也可能作为上游分析 Agent，被后续的网页生成 Agent 调用，为网页生成提供关键风格、交互和功能指导。

### 2. 输出物方向

输出物必须对后续实际产品生成有关键指导作用，而不是只做普通竞品报告。

分析需要按目标区分，不一定每次都完整分析所有内容。核心分为三类：

- 视觉部分
- 交互部分
- 功能部分

不同分析目标应产出不同交付物。

如果分析目标是视觉和交互，输出重点是给网页生成 Agent 提供清晰、准确、可执行的关键描述。

### 3. 验收评分

固定使用整体风格贴合分：

- `overall style-fit >= 0.82`

并拆分为以下维度：

- 视觉
- 结构
- 文案
- 交互
- 合规

### 4. 多竞品融合方式

多个竞品之间不选择单一页面照搬，也不做含糊平均。

处理方式：

- 选取竞品之间的共性作为主参考。
- 从不同竞品中挑选优秀的视觉部分和交互部分进行融合。
- 输出时要说明哪些是共性，哪些是精选融合项。

### 5. 术语可读性

部分 Agent-PD / 工程化名词对用户不够直观。后续产物需要：

- 默认使用中文解释。
- 第一次出现专业名词时附带简短说明。
- 面向设计师的交付物应优先使用设计语言，而不是工程术语。
- 保留必要英文仅限代码、JSON 字段、命令、日志、URL、测试 ID、第三方工具名等。

## 对 T30 规格的修正方向

### Agent 定位

从“通用网页竞品分析 Agent”收窄为：

> 面向设计师和网页生成 Agent 的网页竞品风格/交互/功能分析 Agent。

### 分析模式

应支持按目标选择分析模式：

- `视觉分析`：色彩、字体、版式、留白、图片/视频风格、组件形态、品牌气质。
- `交互分析`：导航、CTA、滚动节奏、动效、反馈、表单/搜索/筛选、关键转化路径。
- `功能分析`：页面模块、信息架构、业务能力、表单字段、列表/卡片规则、用户任务流。
- `综合分析`：同时覆盖视觉、交互、功能，但仍要分区输出，避免混在一起。

### 推荐输出结构

面向设计师：

- 竞品共性总结
- 视觉 DNA
- 交互模式
- 功能模块
- 优秀融合点
- 不应照搬的内容
- 给网页生成 Agent 的提示词/brief
- 验收评分表

面向网页生成 Agent：

- 页面结构建议
- 视觉 token 建议
- 组件规则
- 交互规则
- 文案语气规则
- 禁止复制项
- 验收阈值

## 名词解释

### Agent

可以理解为“带固定工作流程和输出格式的 AI 助手”。它不是普通聊天，而是有明确输入、处理步骤、输出模板和验收标准。

### Agent-PD

一个用来“设计 Agent 的 Agent”。它会把一个想法拆成 Agent 规格、工具、权限、失败处理和测试用例。

### agent_spec

Agent 的规格说明书。里面会写清楚这个 Agent 做什么、输入什么、输出什么、可以用什么工具、不能做什么、怎么判断成功。

### design-only

只做 Agent 设计，不生成可运行代码。适合先把方向定准。

### full pipeline

完整流水线。包括设计 Agent、生成实现、跑测试、自动修复、写入经验。

### maker

负责把 Agent 规格变成实际代码或实现的步骤。可以理解为“生成实现的人/环节”。

### eval

验收测试。用一组规则检查生成的 Agent 是否达到要求。

### review

评审环节。用于判断失败原因属于规格问题、实现问题，还是测试/评审本身的问题。

### FIX_EXHAUSTED

自动修复次数用完了，但实现还没通过测试。不是系统崩溃，而是说明生成代码还需要人工修或重新加强规格。

### style-fit

风格贴合度。用于衡量生成网页和竞品在视觉、结构、文案、交互、合规上的接近程度。

### compliance

合规。这里主要指不能复制竞品 logo、原文、图片、视频、源码或独特品牌资产，只能学习抽象风格和结构规律。

## 下一步建议

下一步不要直接修 `impl.py`，应先把 T30 的推荐规格升级为“设计师友好 + 可被网页生成 Agent 调用”的中文规格，再用这个更清楚的规格重新驱动 Agent-PD 或人工实现。
