# 官网导航架构修正说明

## 结论

如果当前首页顶部导航和产品功能目录都使用锚点滚动到首页模块，这是不符合 T34 PRD、T30 扩展竞品分析和竞品实际做法的。

正确方向应是：顶部导航承载站点级页面跳转；首页只做核心信息预览和入口分发。产品、解决方案、集成、案例、关于、联系等栏目应进入独立页面或页面族。

## 为什么会出现锚点形式

锚点导航通常适合低保真或单页演示阶段，原因是：

- 快速验证首页叙事顺序。
- 减少路由和多页面内容建模工作。
- 方便在一张设计稿或一个原型中浏览完整故事线。

但这只是原型效率考虑，不应该成为正式官网的信息架构。

## 为什么需要改成独立页面

餐饮科技 SaaS 官网的用户决策链路较长。不同用户会分别关注产品能力、系统集成、实施可信度、案例、支持和合作入口。如果所有内容都塞进首页，顶部导航点击后只是滚动到某个模块，会带来几个问题：

- 产品详情深度不够，无法承载场景痛点、关键收益、工作流、集成关系、案例和 FAQ。
- 集成页无法承载搜索、分类、支持状态、请求新集成和合作伙伴申请。
- About / Trust / Contact 的信任与转化功能被弱化。
- SEO 和后续内容运营空间不足。
- 与 Aigens、Deliverect、TabSquare 的成熟 SaaS 页面网络不一致。

## 推荐规则

- 顶部一级导航使用页面跳转，不使用首页锚点替代。
- 首页中的产品矩阵、集成预览、案例预览可以保留，但每个模块都应是摘要，并链接到独立页面。
- 产品功能目录应进入产品总览或对应产品详情页。
- 详情页内部可以使用锚点目录，例如“痛点 / 功能 / 工作流 / 集成 / FAQ”。
- CTA 可以使用锚点滚动到同页表单，但如果是全局联系入口，应跳转到联系页。

## 建议路由

```text
/                         首页
/solutions                解决方案总览
/solutions/chains         连锁餐饮
/solutions/multi-location 多门店营运
/products                 产品总览
/products/orders          订单管理
/products/menu-stores     菜单与门店管理
/products/ordering        自有点餐
/products/delivery        配送编排
/products/data            数据与对账
/integrations             集成目录
/partners                 合作伙伴
/customers                客户案例
/resources                资源 / FAQ / 支持
/about                    关于 / 信任
/contact                  联系我们
```

## 后续生成要求

后续网页生成 Agent 应把 `generator_brief_expanded.json` 的 `required_page_families` 和 T34 PRD 的 MVP 页面清单作为硬约束，不能把多页面栏目降级为首页锚点。
